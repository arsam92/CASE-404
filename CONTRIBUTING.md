# Contributing to CASE 404

Thanks for helping improve CASE 404.

## Before you start

Please read the project README and the relevant documentation under `docs/` before making a change.

For gameplay, UI, localization, engine, or documentation work, keep changes focused so they are easy to review.

## Suggested workflow

1. Fork the repository or create a feature branch when working directly.
2. Make one focused change per pull request.
3. Test the affected part locally before opening the pull request.
4. Explain what changed and how you tested it.
5. Avoid committing generated build artifacts unless the project documentation explicitly requires them.

## Pull requests

A useful pull request should include:

- A clear title describing the change.
- A short summary of the motivation.
- Testing steps or a note explaining why tests were not needed.
- Screenshots for visible UI changes when practical.

For larger changes, open an issue first so the design can be discussed before implementation.

## Code and content

Keep the existing architecture and vanilla JavaScript approach in mind. Prefer small, understandable changes over broad rewrites.

For story and case content, avoid committing spoilers in public-facing documentation unless the file is explicitly marked as containing spoilers.

## Localization

When changing UI strings, update the localization system consistently rather than hard-coding a new language-specific string into the interface.

## Security

Only report or test security issues within systems and environments where you have authorization. Do not include credentials, private data, or exploit instructions for unrelated third-party systems in issues or pull requests.

Thanks for helping make CASE 404 better.
